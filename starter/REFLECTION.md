# Reflection

When I wired up this customer support agent, the design choice I spent the most time on was keeping tool access and memory as separate layers instead of stuffing everything into one giant prompt. Gateway MCP tools handle live order and refund actions, the Knowledge Base tool grounds policy answers in catalog text, and the MemoryHook quietly injects recalled facts before the model sees the user message. That split made each capability easier to test on its own. If the refund Lambda changed, I did not have to touch RAG or memory code. It also mirrors how real support systems work: lookup systems, knowledge articles, and CRM notes are different backends, even when the agent presents them as one conversation.

The concrete challenge that slowed me down was the Knowledge Base system. I created KB in the console, then the first ingestion jobs failed because the KB role could not list the S3 bucket. After fixing the role policy and re-syncing, retrieval finally returned the 15-day electronics return policy. That was a useful reminder that “ACTIVE” on a knowledge base does not mean the data is searchable yet—permissions and ingestion status matter just as much as the resource ID in config.

For a production environment I would harden this in a few ways. The Gateway should not use a NONE authorizer; every tool call needs signed auth and least-privilege IAM. I would add evaluation suites for the six scenarios we ran here, plus guardrails for PII and refund amounts over a threshold that require a human approval step. Memory extraction delay (about 30 seconds) would need clearer UX so customers are not told “I don’t remember” during that window. Finally I would add observability—traces per tool call, latency budgets, and cost alerts on Bedrock invocations—so the team can spot regressions before customers do.
